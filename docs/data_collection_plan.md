# 데이터 수집·평가 담당 시작 계획

담당자: 여희구

## 첫 3일 목표

대량 다운로드 전에 라이선스가 명확한 정제 이미지 1,000장을 확보할 수 있는지 검증한다.

### Day 1: 출처와 라이선스

- `source_inventory.csv`의 후보 에셋 팩을 15개 이상으로 확장한다.
- 각 페이지에서 제작자, 라이선스, 원본 URL을 직접 확인한다.
- CC0를 우선하고 CC BY는 제작자 표시 방법까지 기록한다.
- 무료라고만 적혀 있고 라이선스가 불명확한 자료는 제외한다.

### Day 2: 표본 200~300장

- 후보 에셋 팩에서 표본을 수집한다.
- 합성 시트 분리, 중복 제거, 파일 형식 통일 가능성을 확인한다.
- 50~100장을 `assets.example.json` 구조로 시험 라벨링한다.
- 이미지 한 장당 정제·태깅 시간을 측정한다.

### Day 3: GO 또는 범위 축소

- 라이선스 확인 후 실제 예상 이미지 수를 계산한다.
- 카테고리·색상·속성·시각 스타일별 분포를 확인한다.
- 1,000장 확보가 어렵다면 데이터가 많은 무기 3종으로 줄인다.

## GO 기준

- 정제 예상 이미지 1,000장 이상
- 핵심 무기 카테고리 4종 이상
- 출처·라이선스 연결률 100%
- 필수 라벨 검수 가능률 80% 이상
- 평가 조건 조합 30개 이상

## 저장 규칙

- JSON에는 이미지 바이너리를 넣지 않고 상대 경로만 기록한다.
- 고정 라벨은 `tag_dictionary.json` 값만 사용한다.
- 복수 값은 배열로 저장한다.
- 미확인 값은 추측하지 않고 `null`로 저장한다.
- `null`은 미확인, 빈 배열 `[]`은 확인했지만 해당 속성이 없음을 뜻한다.
- 원본 이미지와 정제 이미지는 같은 `asset_id`로 연결한다.
- 동일 에셋 팩, 동일 제작자 시리즈, 색상 변형은 같은 split에 배정한다.
- train/validation/test는 70/15/15를 시작점으로 사용한다.

## Git 저장 원칙

이미지 원본과 정제 이미지는 대용량이므로 기본 Git 커밋에서 제외한다. Git에는 스키마, 라벨 사전, 출처·라이선스 장부, 수집 스크립트와 작은 예시 파일만 저장한다. 실제 이미지 저장 방식은 재배포 라이선스와 총용량을 확인한 후 Git LFS, 외부 스토리지 또는 다운로드 스크립트 중에서 결정한다.
